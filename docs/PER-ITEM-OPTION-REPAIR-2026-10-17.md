# 多商品换货的属性保留范围修复

## 失败依据

Job `ff4c01c7-e9de-4ab2-8598-9f2d1ac6a1f1`，提交 `410027a`，当前 Kimi BYOK、t2/retail_plus、用例 `0`。
用户提供的对话确认订单读取、规格查询及客户选择均已成功。准备一次包含两种商品的换货时，模型传入公共 `preserve_options=["size","color"]`。旧代码要求每一件原商品同时拥有这两个键，导致没有 color 的商品、没有 size 的另一商品被误判为 `required_option_changed`。

这是 Agent 自定义准备工具的约束范围设计错误，不是 API 字段重命名问题，也不是模型接口故障。

## 改动

- 公共 preserve_options 按每件原商品实际拥有的键校验；所有商品都没有的键仍会报错，不能用拼错的字段跳过校验。
- 新增每个 replacement 自己的 preserve_options，用来表达不同商品各自的保留条件。逐项声明的键必须属于该原商品，且替换项必须保持相同值。
- 逐项条件不能覆盖或取消公共条件。仅使用逐项条件时，公共列表显式填 []；原有公共参数的必填要求保留。
- 原商品属性不存在，不再等同于属性被改动；真正改变了要求保留的属性仍拒绝准备/执行。
- 执行前重新读取和校验全部条件。单次业务请求仍发送完整有序列表，保留重复项。
- REST 的 ItemReplacement 结构不变，实际请求仅含 existing_item_id 和 replacement_item_id；本地保留条件不写入业务 API。
- 工具描述和模型提示说明逐项条件及已接受的候选变化。用户语义仍由模型理解，没有客户话术正则、商品 ID/答案表或新的业务限制。

## 本地验证范围

新增合成数据测试覆盖：异类商品公共属性并集、逐项不同条件、真实保留属性变化、字段拼写/类型错误、执行前事实变化、完整双商品列表只写一次且不泄漏本地约束字段。
已有真实 tau2 REST/SDK/Agent 双商品换货与重放测试改用逐项条件，校验模型可见 schema、确认后一次写入、独立原生 SDK 的数据库结果及新工具集重放结果。
本地模型决策是 mock，不宣称平台用例已通过；当前绑定和用例选择未修改。

实际验证：完整离线回归 213 项通过，25.272 秒；静态打包检查通过，27 个文件、131863 字节、零错误。
