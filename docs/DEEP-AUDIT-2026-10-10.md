这是按既有契约实现模型驱动 Agent 的任务。材料提供了身份、业务政策、REST 和 Agent 消息接口；没有必要自建自然语言规则解析器、业务服务器或逐题答案系统。此前推进到 P7，代表代码模块建设进度，不能代表 Agent 已具备经过真实业务对话验证的完整能力。

## 实际复现并修复的缺陷

### 1. 成功地址写入被误判为 unknown

复现：完整合法地址省略可选 `address_line_2`，分别调用默认地址和订单地址更新。真实本地 REST 后端已完成更新，Agent 工具却返回 `invalid_write_receipt` / `unknown`。

根因：正常 schema 允许该字段省略或为 null；参考 REST 适配器将其转换为历史 address2 的空字符串，并在回执返回 `address_line_2: ""`。原实现将请求模型的 None 与回执的空字符串直接比较。此前 WriteBackend 原样回传请求，未复现后端规范化。

修复：只在回执等价比较中，将第二地址行的省略/null/空字符串视为同一空值。其他字段和非空第二地址行仍精确比较，保留错误地址回执为 unknown 的保护。请求正文不增加猜测字段、不改变后端。

证据：test_reference_runtime 中两类地址 × 四种第二地址行表示，以及真实七类写入测试。修复前两个地址子测试失败；修复后通过。

### 2. 已完成调用的 ID 被模型再次使用便永久停机

复现：第一轮工具调用成功返回；下一次模型完成再次给同一工具相同 ID，原实现直接进入 `invalid_model_reply`。工具参数与业务动作本身可以完全合法。

修复：保留未冲突的 provider ID；对后续完成中与历史冲突的 ID 作确定性的命名空间处理。宿主收到的调用、保存的 assistant 历史和后续 tool 结果均使用同一个规范 ID；不改待返回调用、不改变参数、不修改 provider 原对象、不依赖随机数。单批次空 ID/重复 ID 仍作为无效协议处理。

证据：实际 SDK wire 转换验证连续两轮 `tool_calls[].id` 与 `tool_call_id` 一一对应。

### 3. 无关客户档案变化使确认失效

复现：已回顾并确认地址后，仅新增一个无关订单 ID 或改变其他礼品卡余额，原实现的整个 facts 字典比较拒绝执行。默认地址变化还会使仅修改订单地址的方案失效，混淆两个独立记录。

修复：执行仍重新获取资料、检查身份、本人订单、状态、目标可用性、支付资格及充足余额；版本比较针对该操作的相关记录、金额、目标和方法。目标地址变化、订单状态变化、商品/价格变化等仍要求重新准备和确认。无关订单列表、其他余额、无关默认地址不再阻塞。

证据：实际回顾—用户确认—执行轨迹，以及相关地址变化必须拒绝、零写入的反例。原状态、价格、库存、付款去向变化测试继续保留。

### 4. 一次不合法的模型回复终止整个会话

原行为：错误类型参数、把验证和依赖读取放在同一批次、缺少有效回顾就提议执行，都直接输出永久停止文案。模型没有读取验证反馈并纠正的机会。

修复：仅当本地验证拒绝回复且没有任何工具执行时，允许一次模型纠正。反馈是我们生成的固定协议说明，通过 SystemMessage 传递；不伪造 ToolMessage、不添加客户确认、不执行被拒绝的动作、不将错误提议写入实际工具历史。两次均无效则停止，纠正消耗正常模型调用计数，仍受配置边界约束。

网关/HTTP 异常不进入这条纠正路径，不自动重试模型服务错误。确认与身份门槛保持有效。

证据：错误参数后纠正成功、验证并行批次纠正、重复错误最多两次、模型预算最多一次、无回顾写入只能改为询问客户。全部检查宿主没有执行被拒绝的请求。

### 5. 模型看不到变更参数的完整 schema

原 prepare_change.parameters 和 plan_changes.requests 的内部内容为任意 dict；正确字段仅部分写在描述里。地址键、退款去向、替换列表等需要模型自行推断，增加无效调用概率。

修复：用现有 Address、ItemReplacement 及明确的 Pydantic 参数模型导出地址、取消、付款、商品修改/换货、退货、计划条目的字段、必需项和类型。商品修改与换货共享参数形状，仍由 kind 和工具业务资格检查区分。未增加 REST 字段或操作。

证据：从真实 SDK 最终发送的 function schemas 中核对完整 `$defs`，并执行七类工具和已有契约测试。

## 业务流程复核

| 能力 | 现有实现与材料核对 | 验证与边界 |
|---|---|---|
| 身份 | 模型从完整对话组织邮箱或姓名+ZIP；verify_customer 独立 search，匹配 claimed ID 后才 GET full profile；会话只服务一个已验证客户 | 真实参考 REST 验证公开 t1 seed 的 search→GET；不匹配仅 search。没有用户姓名/邮箱句式正则 |
| 订单 | 当前客户 order_ids 先校验，再 GET 订单并验证 customer_id | 模拟越权/错误列表反例；真实后端七类操作经过这条读取路径 |
| 目录 | 验证后允许与请求相关的公共目录；商品种类、变体、可用变体分开；不靠 ID 文本推产品关系 | 现有目录、比较和权限测试；自然语言偏好排序仍依赖模型 |
| 金额 | calculator/prepare 执行 float 顺序累计与 round(total,2)；不把布尔值或非法金额当零 | 金额边界测试；真实后端修改和换货回执通过。catalog 数字单位 codec 处理结构化选项，不解析用户句子 |
| 取消 | pending 整单；两种规范理由，由模型理解同义表达；逐笔原 charge 原路退款，说明源对应时间 | 真实取消回执、退款序列测试；真实模型的理由和确认判断尚未完整验证 |
| 地址 | 默认/订单地址分别授权；完整回顾，更正后再确认；订单仍须 pending | 本轮修复可选地址行、比较范围；真实两类地址回执通过 |
| 付款 | 一个不同的已保存方法，gift 覆盖全额；新扣旧退，不拆付 | 真实付款回执通过；真实模型选择和澄清待业务对话验证 |
| 商品修改 | pending、同产品、可用变体、保留未改选项、重复数量；完整清单一次提交；等待最后补充问题的回答 | 真实后端成功状态及金额回执；数量/一次性/确认反例。偏好语义没有由真实模型全面验证 |
| 退货 | delivered、完整清单、原支付或请求前已有 gift；accepted 不宣称到账 | 真实后端申请回执与资格测试；真实完整对话待验证 |
| 换货 | delivered、同产品可用目标、一个已存方法结算完整差额；accepted 不宣称发货/退款完成 | 真实后端申请与价差回执；实例歧义必须解释公开能力边界 |
| 多请求 | 同单地址/付款先于一次性商品修改；每步收到回执再处理下一步，保留部分成功 | 模拟依赖/部分失败/撤回轨迹。不能据此宣称真实模型能正确拆解复合意图 |
| 人工 | 模型判断三类政策依据，trusted conversation_id；受理/未知后停止业务 API；成功固定文案 | 真实参考 transfer API、终态 guard；实际人类意图判断待模型验证 |
| 重放 | 工具状态只来自后端、参数和此前工具调用，不读时钟/随机值/跨会话记忆 | 真正调用已安装 SDK Environment.set_state，验证验证→准备→回顾→取消的状态及真实后端一致 |

参考后端测试直接调用 toolkit，验证 REST 和回执，不证明客户已同意；确认语义仍由模型负责。实际 Agent 编排的回顾/后续用户轮次由现有确认测试检查，模型决策部分是夹具。

## 为什么旧测试不足

1. provider Mock 直接给出正确工具名、参数和最终答案，不能验证模型理解。这类测试有价值，但只验证工具和消息编排。
2. 直接生成 ToolMessage 或模拟 REST 回执，绕过 SDK 消息序列化/参考业务适配。P1 缺少 MultiToolMessage→单个 ToolMessage 投影，真实第二次模型调用会缺少对应工具结果；此前已修复。地址回执问题同样由模拟适配掩盖。
3. 本轮 SDK 重放测试最初也手工用 json.dumps 生成记录，暴露测试路径差异：普通 Environment 对 dict 中数字/布尔值进行字符串序列化。已经改成 live/replay 都使用真实 get_response，未修改 SDK、未放宽重放校验。生产 sealed 环境还带有可信 API trace 重放路径；本地这项测试不能替代平台容器验证。
4. 134 条公开需求的映射是需求整理，不是 134 条业务对话通过。不能用测试总数或“P7完成”替代业务验收。
5. 上次真实模型测试只完成六条身份/历史恢复对话；第七条读取失败恢复受授权的16次调用上限停止。没有对七类写入、修改确认、多请求、人工语义作完整真实模型验收。中文邮箱回答曾额外带出姓名/地址，虽已加强提示，不能把未复测的提示修改说成已验证。

## 最新平台 t1 与本地模型的差别

平台 Job `c6465c7c-8e13-4383-b9dd-1a0acee50f4b`，GitHub run `38035706842`，提交 `24511a7`：0/1，首次 gateway_generate 报 `provider_rate_limit`、429、model_broker、reported RateLimitError，无工具调用。

宿主 model broker 捕获模型服务异常，以 type/message 封装返回；候选 SDK 将其抛成 RuntimeError。当前诊断恢复可保留的类型与状态码，并没有把所有根因认定成 RuntimeError。此报告的失败发生在取得模型决策之前，不是姓名解析、verify_customer 或业务 API 已执行失败。

本地调用用授权的 Moonshot 中国端点、Kimi 和独立账户，平台调用使用它注入的配置与凭证，两者共享 Agent 代码与模型—工具协议，不共享模型服务账户、限流窗口和运行环境。上次16个真实 HTTP请求均200，说明那条本地路径可运行；不能推出平台当时也必然200。

代码自己的工程边界仍为128次模型尝试/会话、16个工具批次/用户请求、每方案3次未知写入观察，属于工程配置，不是业务锁定政策或模型服务商429。此次首次模型调用未触及前两项。没有通过改变绑定、改自带模型直连或自动重复推送来绕过失败。

429 的进一步定位应读取对应平台 provider 请求的脱敏 code/type、route、request_id、Retry-After 等宿主日志。此前课程诊断接口返回404而未提供这些字段；公开报告足以定位模型服务请求阶段，不能据此具体断言是哪一种配额。此项日志需求不妨碍本轮修复已复现的代码错误。
