# 面向业务完成的 Agent 核查与修复

基线：`da9933c867b83784ece66367bbcd303f269c2af7`。本轮修改尚未提交或推送。仓库、分支、工作流、平台绑定、模型参数及评测范围均未修改。

## 核查原则

目标是模型自主理解多轮真实请求、使用工具取得依据，并完成客户授权的实际操作。工具检查可验证的身份、归属、规格、数量、资金和接口事实；不使用用户句式正则、关键词路由、用例编号分支或预制业务答案替代模型决策。

检查依据包括原始材料的有效政策登记及其原文、U1–U6、OpenAPI、Agent/Client API 契约和本地真实 tau2 SDK。既有的 134 条公开要求索引用于核查能力覆盖，不作为运行时答案表，也不等同于已通过全部评测。

## 发现及修改

| 问题 | 修改 | 业务影响 |
|---|---|---|
| 正确自然语言回顾后仍可能因缺少内部 `review_change` 而无法执行 | 成功准备结果直接进入待展示方案；模型解释并回答问题，程序补充精确事实摘要，记录实际展示版本 | 不再依赖模型重复读取同一草案；后续明确批准即可执行 |
| 固定内部 JSON 替代了客户问题的回答 | 取消提前返回固定 JSON 的路径；保留模型说明，只补充本次变更涉及的商品、规格、金额、结算方法和确认问题 | 客户可以了解退款和寄回流程，而不是只收到内部数据 |
| 草案 facts 中写着 request accepted | 改为明确的未提交草案状态 | 不把准备误当成业务完成 |
| 方案、暂停和执行结果在 Agent 状态中不同步 | 同步 superseded/withdrawn/paused/accepted/completed 等状态；执行错误清除原展示授权记录 | 不复用失效方案，不丢失已完成结果 |
| 所有执行工具始终暴露，容易误选无关写入或混用政策 | 仅向模型暴露已有展示方案且存在后续客户输入的执行种类；模型仍判断是否真正批准 | 减少错误操作选择，程序不将任意后续输入当作同意 |
| 多个独立请求被迫分别走重复确认流程 | 可先准备多个独立方案，一并展示后取得明确联合批准，再逐项执行并保留回执 | 支持真实复合请求；有依赖的地址/付款/商品操作继续按实际依赖顺序处理 |
| 仅能给客户一串订单 ID，再让客户猜是哪单 | `list_customer_orders(include_details=True)` 通过现有 API 读取本人订单并逐一检查归属 | 模型可从实际商品记录找订单，不解析 ID 或猜日期 |
| 目录可售数量与总变体数量容易混淆 | `get_catalog_summary(product_id=...)` 返回该产品实际总数与可售数；空参数保持全店统计 | 不再把缺货项计入可售数量 |
| 通用提示中混放不同业务时效，真实模型曾把取消时效套到换货 | 增加有来源的按操作政策，准备结果携带相关政策，提供 `get_service_policy`；实际换货回执明确无已知到账时效 | 换货不再借用其他业务退款时效，不承诺未知标签、物流日期或已到账 |
| 单个共享 preserve_options 必填，工具使用负担大 | 默认空列表，继续支持每件商品的明确保留条件 | 不因缺少空的辅助字段拒绝有效业务参数；实际保留要求继续严格核对 |
| 未知结果只允许检查三次，属于额外工程限制 | 移除这道只读次数限制，保留原写入不可重试和未知结果保护 | 允许必要查证，观察结果不授权再次写入 |
| 模型收到重复的完整订单/客户快照，易混淆变更范围 | 模型投影只展示当前方案相关信息，原始会话证据及工具快照保持完整；提供可信进度摘要 | 提高实际操作目标清晰度，不向客户重复无关个人资料 |

`review_change` 保留用于可选重取旧方案和历史兼容；旧版固定 JSON 回顾也可重放。当前新路径不需要该额外调用。新方案摘要是从真实工具结果生成的事实展示，并非用户语言解析或同意判断。

- 换付款规则及时效：email_09 / email_08 / email_07。

### 本轮真实模型

使用用户本轮授权的 Kimi 中国 API，**累计 16 次实际请求，全部 HTTP 200**。无 HTTP 或空响应失败后的自动重试。按全部输入未命中缓存保守估算 **1.1057870 元**，低于 10 元上限；这不是供应商账单。估价依据：[官方 K2.6 定价](https://www.kimi.com/resources/kimi-k2-6-pricing)。

1. 公开 t1 同样的输入：模型自主调用 verify_customer，传入邮箱和声明的客户 ID；真实 API 先独立 search，再读取该客户详情，正常回答真实邮箱。2 次请求。
2. 隔离环境重建用户给出的换货数据：模型自主核验姓名/邮编、读取订单和库存、处理缺货替代、准备两件方案、回答客户问题，在客户随后明确批准后调用 execute_exchange。12 次请求。只写入一次 `/v1/orders/%23W6211689/exchanges`，对应关系及结算方法正确，状态 `exchange requested`，差价 `-71.06`，未调用 review_change。
3. 逐句检查发现首次完整对话虽已正确登记业务，但错误套用了其他业务的退款时效。修复操作政策上下文后，用本轮剩余 2 次调用回放真实历史，分别核查提交前问题和接受后的说明：提交前保持零写入，并明确换货到账时间未指定；接受后正确区分申请受理与退款/发货完成。

真实模型测试客户发言由脚本提供；所有 Agent 决策来自真实模型，业务工具及数据库为真实本地 SDK。后两次历史回放因新增政策说明字段，不比较旧版工具响应的完整文本；实际工具仍被回放，且检查数据库状态。完整离线当前版本重放测试仍使用正常校验。

本地宿主测试固定 `max_tokens=4096`、供应商默认 thinking；这是本地测试配置，未覆盖或更改平台注入参数。新加入的联合确认逻辑由最后一轮离线 SDK 测试验证，尚未另跑付费模型。
