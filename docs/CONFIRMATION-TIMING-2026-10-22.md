# 确认时机修复

## 问题

用例 0 的 Agent 在已取得订单、两项替换选择和差价后，询问完整清单及结算方式，并说确认后才准备方案。当前提示词将完整清单的确认与等待回复写成准备前的前置阶段；工具说明也要求准备前收集完整清单，却没有区分“已知请求内容”和“明确确认清单完整”。随后还要求展示实际方案、再等待提交同意，额外增加了准备阶段的授权关卡。

## 材料与边界

- 原始 `case_file_06.md`：完整商品清单应在提交前明确，草案可以在尚未确认完整性时存在。
- 原始 `case_file_03.md`：展示具体换货内容、核实清单并取得明确同意后才提交。
- 原始 `case_file_40.md`：整个差价使用一种结算方式；选择方式、审阅和实际提交不是同一状态。
- 当前 `INTERFACE-CLARIFICATIONS.md` U5：写入前确认完整清单。

这些要求不能扩展为“读取、计算、准备、展示也必须先获得操作同意”。这次修改不取消执行前确认，也不规定固定对话轮数；方案变更、信息缺失和选择有歧义时仍需澄清。

## 修改

事实齐全时直接调用只读 `prepare_change`、`review_change`；准备阶段不等待额外授权或清单完整性声明。实际方案展示商品、替换规格、差价、结算方式，并在写入前取得完整清单和该方案的明确同意。仅有一个合格的已保存结算方式时，可将它作为建议列入待确认方案；存在多个可选方式时仍先澄清客户选择。

`state.py` 的实际方案展示及后续客户输入检查、写入执行器、REST 请求和评测范围均未修改。SDK 回归覆盖：一次客户请求内可以连续完成读取、准备和展示，零业务写入；后续明确确认后才执行一次换货请求，并与原生 SDK 和回放结果一致。
