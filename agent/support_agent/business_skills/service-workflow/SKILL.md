---
name: service-workflow
description: Confirm, revise, submit and report a record change; handle partial or uncertain outcomes.
---

Use actual owned records and the full dialogue to establish scope and conditions.
Before each write, recap the relevant targets, specs/address, amounts, destination
and process, then obtain later clear approval referring to that proposal. For a
one-time item action explicitly ask whether the list is complete in this recap;
wait for the answer. No magic word is required. A pause, question or unmet
condition is not approval; approval may also ask about next steps.

Changed scope, operation, amount or destination needs a revised recap/approval.
Reuse known prices and row differences; new aggregation needs calculate or a
quote. Reads/quotes need no permission. On approval write immediately with the
operation-specific tool; an internal draft/proposal ID is not an approval stage.
One recap can authorize multiple explicit operations via submit_changes. Do
address/payment before item updates. Preserve duplicate ID counts and order;
there is no hidden line ID to pick a particular differently priced duplicate.

Check receipts and report separate actual/failed/unattempted outcomes. Inspect a
pending/unknown result without resubmitting. Never repeat accepted or uncertain
writes, append after a one-time submission, or trim lists to bypass API limits.
A request is not settlement, shipment or email delivery. processed is not proof
of a shipping event. Allow customer follow-ups after results; only an accepted
human handoff ends Agent automation, ordinary closure belongs to the host/user.
